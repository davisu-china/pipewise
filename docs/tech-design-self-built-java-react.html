01方案摘要与关键决策

PRD 附录 A 的原始建议是「执行内核不自研，嵌入 DBOS / Restate / Temporal」。本方案按项目决策改为纯自研：不自研通用 durable execution 平台，只自研流程引擎所需的持久化状态机 + 作业队列 + 幂等重放，范围可控、可测试、可演进。Flowable 及任何 BPMN 引擎均不进入依赖树。

1.1 一句话架构

架构摘要 Spring Boot 模块化单体拆成 api 与 engine 两种运行形态：API 只做同步读写与鉴权；Engine 从 PostgreSQL 的 wf_execution_job 表中领取作业，以「实例级串行 + 令牌驱动」推进流程，所有状态变更、审计、Outbox 事件在同一个数据库事务内提交；RocketMQ 负责事务提交后的异步投递，Redis 只做缓存与限流，MinIO 存附件与导出文件。

1.2 关键选型

维度选择决策理由
执行内核自研令牌引擎（Token / NodeInstance / SignSession）PRD 的签核语义（或签/并签/竞签、加签、退回重提）与 BPMN 差异大；自研可让「语义即模型」，避免在引擎扩展点上打补丁
事实源PostgreSQL 16事务、行锁、SKIP LOCKED、advisory lock、JSONB、GIN、声明式分区，一个库覆盖运行态与审计
作业调度PG 作业表 + 租约（lease）+ 心跳避免引入额外调度中间件；作业可审计、可重放；RocketMQ 不承担「状态权威」
消息RocketMQ 5.x + Outbox 模式事务内落 Outbox，事务后投递；保证「不全丢、可重放」，消费端按事件 ID 幂等
缓存Redis 7只做加速：版本快照、组织架构、幂等热键、限流、任务角标推送；任何 Redis 数据丢失都不影响正确性
对象存储MinIO（S3 协议）附件、图片、导出文件、归档包；预签名直传 + 服务端确认

表达式AviatorScript 白名单子集轻量、可编译缓存、无反射；只读、无副作用，复杂逻辑强制落脚本
后端框架Java 21 + Spring Boot 3.5 + MyBatis + Flyway虚拟线程承载 IO；MyBatis 对引擎热路径 SQL 可控；Flyway 管理 schema 演进
前端React 18 + TypeScript + Vite + shadcn/ui + React Flow与现有 web/ 工程一致；React Flow 承担画布；Schema 驱动的自研表单渲染器
部署模块化单体，按 profile 拆进程MVP 阶段一套代码、两个进程，降低运维复杂度；后续可独立扩缩容

Flowable 与自研的取舍

维度Flowable 7自研内核
签核语义多实例任务可做会签，但或签/竞签/加签/退回重提需要大量扩展与自定义监听器签核会话语义原生建模，三种模式由同一裁决函数表达

可控性行为受引擎默认语义约束，遇到边界要读源码或绕行每个状态转移都在自己代码里，可测试、可审计、可演进

结论：本项目对签核语义、表单权限与运维干预有大量定制需求，Flowable 的扩展成本会持续累积；按项目决策采用自研，并用 M0 门槛与模型测试控制风险。

仓库现状说明 当前 java-mvp/ 是基于 Flowable 7 的可运行验证骨架，仅用于验证「定义 → 实例 → 审批 → 结束」闭环；本方案落地时不复用其引擎层，新建 server/ 模块承载自研内核，java-mvp/ 在 M1 完成后归档删除。backend/（Python MVP）作为行为语义参考，不作为生产实现。

1.4 自研边界：我们到底在自研什么

在范围内

流程实例内部的持久化状态转移、令牌流转、作业重放、签核裁决、超时与回调唤醒、版本钉住、审计与 Outbox。

不在范围内

通用分布式事务、任意代码的 exactly-once、跨系统两阶段提交、通用任务编排（DAG 调度）、RPA 执行器。

正确性目标

人工任务严格一次；状态转移至少一次执行 + 幂等收敛为一次效果；外部副作用通过幂等键收敛。

失败处理原则

任何无法自动恢复的异常，实例进入 FAILED 或节点挂起并告警，绝不在状态不明时继续推进。

03执行内核：令牌与状态机

内核只做一件事：在不可变图快照上，维护「令牌在节点间流动」的持久化状态。所有业务差异由节点配置、表单与脚本表达，内核不为任何业务分支写代码。

3.1 领域模型与不变量

对象表职责关键约束
流程定义wf_definition稳定业务标识（key），跨版本不变(tenant_id, key) 唯一
流程版本wf_definition_version发布时冻结的图快照，运行期只读发布后不可修改；版本号单调递增
流程实例wf_instance一次运行，钉住 version_id 与表单版本(tenant_id, definition_key, business_key) 唯一
令牌wf_token执行游标；并行时多个令牌共存一个令牌同一时刻只在一个节点；消费后不可复活
节点实例wf_node_instance某节点的一次激活，持有局部上下文同一令牌 + 节点 + 轮次最多一条 ACTIVE/WAITING 记录
签核会话wf_sign_session一个人工节点上的裁决集合每个节点实例最多一个 OPEN 会话
任务wf_task指派给具体人的待办状态机单调；完成必须 CAS 版本号
变量wf_variable流程级上下文当前值(instance_id, scope, name) 唯一；带 version
作业wf_execution_job一次待执行的引擎步进租约到期可重领；处理必须幂等
六条不变量（代码评审的硬标准）
  1. 任何状态变更必须在数据库事务内完成，并同时递增实例的 state_version。
  2. 令牌只能被消费一次；消费动作与后继令牌创建在同一事务。
  3. 节点实例状态单调前进，不允许从终态回到非终态。
  4. 并行分支不共享可写的局部上下文；写流程级变量必须经过版本号 CAS。
  5. 外部副作用（HTTP、MQ、通知、Webhook）不进入数据库事务，统一走 Outbox 或两阶段作业。
  6. 实例只有在「没有 ACTIVE 令牌、没有 WAITING 节点实例」时才可判定完成。

3.2 令牌驱动执行模型

令牌（token）是执行游标。节点激活时创建一个节点实例，令牌挂在该节点上；节点完成后消费令牌并为其每条出边各创建一个新令牌。并行 fork 即「一个令牌消费、多个令牌产生」，并行 join 即「多个令牌到达、合并为一个」。这样并行、嵌套并行、回环都不需要额外状态字段。

图 3-1 并行分叉与汇聚：Fork 消费 T1 产生 T2/T3，Join 收到两条令牌后合并为一条继续。

令牌字段与状态

wf_token(
  id            BIGSERIAL PRIMARY KEY,
  instance_id   VARCHAR(40) NOT NULL,
  node_id       VARCHAR(64) NOT NULL,
  status        VARCHAR(16) NOT NULL, -- ACTIVE / WAITING / CONSUMED / CANCELLED
  parent_token_id BIGINT,             -- 由哪条令牌分叉而来
  scope_id      BIGINT,               -- 所属并行/包容作用域（join 配对用）
  branch_key    VARCHAR(64),          -- 分支标识（可选，便于排障）

WAITING 表示令牌已到达节点但节点在等外部事件（人工任务、定时器、回调、子流程），对应节点实例也是 WAITING；ACTIVE 表示待引擎继续推进；CONSUMED 表示已被节点消费并产生后继。

3.4 一次引擎步进

每个作业（job）代表一次「在某个节点实例上做一次确定性推进」。处理流程固定为：加实例锁 → 状态校验 → 执行器计算 → 原子落库 → 提交。执行器内部不直接写库，只产出变更指令（Command），便于测试与回放。

// pw-engine: EngineWorker
@Transactional
public void process(Job job) {
    lockInstance(job.instanceId());                 // pg_advisory_xact_lock(hash(instanceId))
    Instance inst = instanceRepo.loadForUpdate(job.instanceId());
    if (inst.status().isTerminal()) { jobRepo.done(job); return; }

    NodeInstance ni = nodeRepo.load(job.nodeInstanceId());
    if (!ni.status().equals(job.expectedStatus())) { // 重复投递 / 已被处理
        jobRepo.done(job); return;                   // 幂等空操作
    }

    Snapshot snap = snapshotCache.get(inst.versionId()); // 不可变，命中率接近 100%
    Node node = snap.node(ni.nodeId());
    StepResult result = executorRegistry.get(node.type())
        .execute(new StepContext(inst, ni, node, snap, job));

    commandApplier.apply(result.commands());        // token / node / task / var / timer / job
    instanceRepo.bumpStateVersion(inst, result.stepDelta());
    audit.append(inst, result.auditEvents());
    outbox.append(inst, result.domainEvents());     // 同事务，事务提交后投递
    jobRepo.done(job);
}

3.6 网关与汇聚算法

排他网关（XOR）

  • 出边按快照中的顺序求值（设计器保存顺序即优先级），第一条为 true 的边被选中。
  • 校验期强制存在默认边（条件为 true 或显式 default: true）；运行期若仍无匹配，走默认边并记 GATEWAY_NO_MATCH 告警事件。
  • 表达式只读上下文，不允许赋值与函数副作用；求值超时 50ms。

并行网关（AND）

fork:
  scope = new JoinScope(forkNodeId, pairedJoinNodeId, expected = outgoingEdges)
  consume(token)
  for edge in outgoingEdges: createToken(edge.to, scope, branch=edge.id)

join:
  scope.arrive(token.branchKey)
  if scope.arrived == scope.expected:
      consume(all arrived tokens); close(scope)
      createToken(join.outgoing[0])
  else:
      token.status = WAITING; node.status = WAITING

JoinScope 持久化在 wf_join_scope（含 expected_branches、arrived_branches、parent_scope_id），因此进程崩溃后仍能判断「还差哪条分支」。嵌套并行的 scope 形成树，深度默认限制 3 层。

包容网关（OR）

  • fork 时对全部出边求值，激活所有为真的分支（至少一条，否则走默认边）。
  • fork 把「实际激活集合」写入 scope；join 只等待该集合内的分支。
  • join 的匹配范围必须在设计期由 fork 配对确定，禁止一个 join 被多个 fork 复用（校验期阻断）。

死锁与循环保护

3.7 实例完成判定

结束节点消费令牌后，在事务内检查：该实例是否还存在 ACTIVE/WAITING 令牌，或非终态的节点实例。若都不存在，置实例 COMPLETED，记录 outcome（approve / reject / terminated），写入结束事件，并触发结束回调（Outbox）。

常见错误：只看「到达 end 的令牌数」 并行实例中一条分支已到 end，另一条仍在审批，实例不能完成。完成判定必须基于「全局是否还有活动令牌」，而不是单条令牌的位置。

自研内核的可靠性不来自「不崩溃」，而来自「崩溃后能确定地接着跑」。本章定义作业模型、租约、实例级串行、恢复矩阵与幂等体系。

4.2 领取、租约与回收

-- Worker 批量领取（PG 9.5+ SKIP LOCKED）
WITH picked AS (
  SELECT id FROM wf_execution_job
  WHERE status = 'PENDING' AND available_at <= now()
  ORDER BY priority, id
  LIMIT #{batch}
  FOR UPDATE SKIP LOCKED
)
UPDATE wf_execution_job j
SET status='RUNNING', worker_id=#{workerId},
    lease_until=now() + interval '30 seconds',
    attempts=attempts+1, updated_at=now()
FROM picked WHERE j.id=picked.id
RETURNING j.*;
  • 心跳：长任务每 10s 续租；续租失败说明作业已被回收，立即停止写入（避免双写）。
  • 回收器：每 10s 扫描 status='RUNNING' AND lease_until < now()，重置为 PENDING；超过 max_attempts 置 DEAD 并告警。
  • 退避：失败重试按 min(2^attempts, 300)s 计算 available_at，避免故障时风暴。
  • 优雅停机：停止领取 → 等待在途作业完成或租约到期 → 退出。

4.3 实例级串行

同一个实例的并发推进（双击提交、重复消息、两个 Worker 同时领到作业）必须串行化。采用 PostgreSQL 事务级 advisory lock，锁粒度就是实例：

SELECT pg_advisory_xact_lock(hashtextextended(#{instanceId}, 0));
-- 或对 wf_instance 行加 FOR UPDATE
SELECT * FROM wf_instance WHERE id = #{instanceId} FOR UPDATE;

为什么不用 Redis 分布式锁

锁的持有者崩溃后只能等过期，且锁与数据库事务不在同一原子边界。advisory lock 随事务自动释放，不会出现「锁过期但事务还在跑」。

锁顺序

固定顺序：实例 → 任务 → 变量（按 name 排序）。跨实例操作（子流程、迁移）按实例 ID 升序加锁，避免死锁。

裁决算法（统一入口）

// 在实例锁内执行，session 行 FOR UPDATE
void onTaskCompleted(Session s, Task t, Verdict v) {
    s.completedCount++;
    if (v == APPROVE) s.approveCount++;
    if (v == REJECT)  s.rejectCount++;

    switch (s.mode) {
      case ANY -> {
        if (v == APPROVE) return decide(s, APPROVE);          // 任一同意即通过
        if (s.completedCount == s.expectedCount) return decide(s, REJECT); // 全否决
      }
      case ALL -> {
        if (v == REJECT && s.rejectRule == VETO_IMMEDIATE) return decide(s, REJECT);
        if (passRuleSatisfied(s)) return decide(s, APPROVE);   // 全同意或达比例
        if (s.completedCount == s.expectedCount) return decide(s, REJECT);
        if (s.signStyle == SERIAL && v == APPROVE) activateNextTurn(s);
      }
      case RACE -> decide(s, v == APPROVE ? APPROVE : REJECT); // 第一人定音
    }
}

boolean passRuleSatisfied(Session s) {
    return switch (s.passRule.type) {
      case "ALL"   -> s.approveCount == s.expectedCount;
      case "RATIO" -> s.approveCount * 1.0 / s.expectedCount
                        >= s.passRule.ratio.doubleValue();
    };
}
或签最常见的实现错误 把「任一否决」当成节点否决。PRD 口径是：或签的否决只是意见记录，节点仍等其他人；只有「全部人都否决」或「全部结束后仍无人同意」才裁决否决。代码评审必须覆盖这个用例。

5.3 并行会签与串行会签

  • 并行：一次性创建全部任务，expected_count = 候选人数。
  • 串行：只创建当前轮次任务；上一人同意后创建下一个，expected_count 保持总人数不变。任一环节否决按 reject_rule 处理。
  • 串行会签的超时从「任务创建」开始计，不包含排队等待时间；节点总 SLA 另配。

6.2 快照与不可变性

  • 发布时把设计态完整序列化为 snapshot_json，并计算 SHA-256 存入 content_hash；任何字节变化都会产生新哈希。
  • 快照包含：节点、边、变量声明、表单绑定、字段权限矩阵、脚本版本引用、超时策略、审批人解析器、灰度规则。
  • 实例创建时记录 version_id 与 snapshot_hash；运行期只读快照，不反查设计态。
  • 脚本与表单以「版本 ID」引用，而非内容内联，避免快照过大；引用版本同样不可变。
  • 快照缓存于 Redis（key 含 hash），进程内再有 Caffeine 一级缓存；发布时按 key 失效。

6.3 灰度与默认版本

灰度维度规则实例选择方式

发起人用户/部门白名单匹配 initiator 或其部门
比例0–100%hash(business_key) % 100 < ratio，同一业务键稳定命中

灰度规则随版本发布生效；命中结果写入实例（version_id + gray_bucket），便于事后解释「为什么这个实例走了 v2」。

6.4 下线保护

  • 下线版本只阻断新实例创建；运行中实例继续使用原版本。
  • 下线前展示钉在该版本的运行中实例数量与最早开始时间。
  • 不允许删除任何已发布版本；历史版本永久保留用于审计与回溯。
  • 默认版本切换是独立操作，与发布解耦，避免「发布即全量」。

权限前端服务端

7.4 表单与上下文双向绑定

  • 字段 key 直接映射流程变量名；提交时按权限矩阵过滤后写入 wf_variable（流程级）。
  • 节点局部字段先写 wf_node_instance.local_context，按节点配置的 outputMapping 合并到流程级。
  • 脚本修改上下文后，表单再次打开时展示最新值；提交前前端重新拉取 GET /instances/{id}/form，避免基于旧值提交。
  • 文件字段只存 MinIO 对象 key；表单数据里保存 {key, filename, size, sha256}。

7.6 子表单、联动与计算（P1）

  • 子表单：最多 200 行（服务端硬限制）；支持行内校验、列合计；脚本可按整体数组读写。
  • 联动：字段 A 变化触发 B 的取值/显隐/必填/选项；联动规则在客户端执行，服务端在提交时按同一规则复核关键项。
  • 计算字段：前端实时计算仅用于展示；服务端提交时强制复算并以服务端结果为准，防止篡改。
  • 数据源：静态字典（本地缓存）、接口动态拉取（超时 3s、结果缓存、失败降级为空）、级联数据源。
  • 复杂联动一律建议落到脚本节点，表单只负责展示与采集，避免规则引擎变成第二套编程语言。

7.8 草稿、版本与附件

  • 草稿：存 wf_form_draft，不启动实例、不产生待办、不发通知；草稿与正式提交隔离。
  • 版本钉住：实例创建时记录所用表单版本；表单升级不影响旧实例，旧实例按旧 Schema 渲染。
  • 附件：前端向 MinIO 申请预签名上传 URL（5 分钟有效）→ 直传 → 调确认接口登记 wf_attachment；确认时校验大小、类型、SHA-256。
  • 打印/导出：服务端生成 PDF（含流转记录与意见）与 Excel；生成任务异步执行，结果存 MinIO，链接短时有效。

7.9 表单提交与任务完成的原子性

POST /api/v1/tasks/{taskId}/submit-form
  ├─ 鉴权：任务确实指派给当前用户（或管理员代操作）
  ├─ 加载绑定矩阵，过滤提交体
  ├─ 服务端复算计算字段
  ├─ 三层校验（提交层 + 流转前层）
  ├─ 事务开始（实例锁）
  │   ├─ 写 wf_form_data（本轮生效数据）
  │   ├─ 写 wf_variable（带版本号）
  │   ├─ 完成任务 + 签核裁决
  │   ├─ 推进令牌 / 创建后继任务
  │   ├─ 写审计与 Outbox
  │   └─ 提交
  └─ 返回新任务或实例状态

校验、写表单、写上下文、完成任务、流转令牌必须在同一事务内，绝不允许「表单存了但流程没走」或反之。竞签场景下，后到者的提交在任务已被取消时直接返回 TASK_ALREADY_FINISHED，其表单数据不落库，仅保留审计。

两阶段执行与重试

  1. Java 侧加载上下文快照与脚本版本，调用 Runner，记录 script_run（入参哈希、耗时、结果摘要）。
  2. Runner 返回补丁后，Java 开事务、校验实例状态与变量版本，写入补丁；版本冲突按 8.3 策略处理。
  3. 失败重试：默认最多 3 次，指数退避；重试复用同一 script_run_id，保证审计可追踪。
  4. 仍失败：走 onError 出边；无兜底则节点 FAILED、实例挂起并告警。

脚本版本与试算

  • 脚本独立存储于 wf_script / wf_script_version，发布后不可变；快照引用 script_version_id。
  • 设计器提供「试算」：输入模拟上下文，返回输出、日志、耗时，不影响任何实例。
  • 脚本变更必须走发布流程；已发布版本的脚本不可原地修改。

9.2 Webhook 回调

  • 订阅方按事件类型与流程 key 订阅；URL 必须 HTTPS（或内网白名单）。
  • 请求头：X-PipeWise-Event、X-PipeWise-Delivery（UUID）、X-PipeWise-Timestamp、X-PipeWise-Signature（HMAC-SHA256，签名体含时间戳防重放）。
  • 重试：5s / 30s / 2m / 10m / 1h，最多 8 次；超限进入死信表并告警，可在运维后台手动重放。
  • 2xx 视为成功；非 2xx 或超时（10s）视为失败。
  • 投递记录独立于业务事务，可查询每次请求与响应摘要。

9.5 子流程（P1）

  • 内嵌子流程：同一实例内创建子作用域令牌，共享实例生命周期；输入输出通过映射。
  • 调用外部流程：创建子实例（记录 parent_instance_id），父节点 WAITING；子实例结束时通过 Outbox 事件唤醒父流程。
  • 失败策略：子流程失败时父流程按配置「挂起 / 走异常边 / 终止」。
  • 子实例的版本独立钉住；父实例迁移不影响子实例。

11.5 约定

  • ID：实例使用 inst_ + ULID（可排序、无中心依赖）；内部表用 BIGSERIAL；事件用 UUID。
  • 时间：全部 TIMESTAMPTZ，存 UTC；应用层按用户时区展示。
  • 租户：所有业务表带 tenant_id，唯一索引包含租户；P2 前默认 default。
  • 软删：定义用 RETIRED 状态代替删除；运行态不允许删除，只归档。
  • 枚举：数据库存字符串常量，应用层用枚举校验，避免数字魔法值。
  • 大字段：快照、表单 Schema、脚本正文存 JSONB/TEXT；单条超过 1MB 时改为 MinIO 引用。

14技术难点专章

以下问题决定自研内核能否成立。每项都给出「为什么难、方案、验收标准」，M0 阶段优先验证前四项。

14.1 令牌与汇聚的正确性

为什么难

并行分支、嵌套并行、条件跳过、回环叠加时，很容易出现「某条分支静默丢失」或「join 永远等不齐」。这类 bug 在测试环境不显眼，上线后表现为实例永久卡住。

方案

令牌模型 + 持久化 join scope（记录期望分支与实际到达）；fork/join 发布期强制配对；嵌套深度限制；死锁检测与告警；不自动跳过分支。

验收

状态机模型测试覆盖 fork/join 全部组合（含嵌套 3 层、条件跳过、回环）；构造 1000 个随机图与随机完成顺序，验证汇聚结果唯一且无丢分支。

兜底

实例卡住检测任务：同一 join scope WAITING 超过阈值告警；运维可查看「还差哪条分支」。

14.2 崩溃恢复与「效果恰好一次」

为什么难

进程可能在任意指令间崩溃：事务提交前、提交后标记完成前、外部调用后写库前。自研内核必须让每种中断都能收敛，而不是依赖「不崩溃」。

方案

状态变更与作业完成在同一事务；作业租约 + 重领；处理前校验 expected_status；外部副作用走 Outbox 或带幂等键的两阶段；脚本只返回补丁。

验收

故障注入：在事务提交前后、作业标记前后、Outbox 投递前后杀进程；恢复后断言实例状态与事件数量符合预期，无重复任务、无重复流转。

边界

不承诺外部系统副作用恰好一次；由幂等键 + 下游配合达成效果一次，文档与 SDK 明确声明。

14.3 并发与幂等

为什么难

双击提交、重复消息、两个 Worker 领到同一实例、竞签两人同时提交、并行分支写同一变量，都会造成重复流转或丢更新。

方案

实例级 advisory lock；任务与变量版本号 CAS；幂等键；竞签在会话行锁内裁决；变量冲突策略；作业重复投递空操作。

验收

并发压测：同一任务 100 并发提交，仅 1 次成功；竞签 50 并发，结论唯一且其余任务全部取消；并行写变量冲突全部被捕获。

监控

版本冲突率、重复作业空操作率、锁等待时间；异常升高时告警。

14.4 签核语义的一致性

为什么难

或签与竞签只差「否决算不算数」；加签、转交、串行会签会让计数与裁决规则交叉；业务方对「会签比例」理解不一致。

方案

任务与会话分离；统一裁决函数；三种模式的决策表固化为单元测试；加签只改会话人数不换模式；设计器显式展示当前语义。

验收

三种模式 × 并行/串行 × 同意/否决/加签/转交，穷举动作序列，断言裁决结果；PRD §8.1 的「或签 vs 竞签」用例作为回归基线。

口径冻结

PRD 第 8 章作为唯一语义来源；任何扩展先改 PRD 再改代码，避免实现漂移。

14.5 长跑实例与版本迁移

为什么难

实例可能存活数月，期间定义发布多版。强制迁移会让在途令牌落在不存在的节点上；不迁移则旧 bug 长期存在。

方案

默认不迁移；实例钉住快照；显式迁移工具做静态 diff + 活动映射 + 预演 + 白名单 + 快照回滚；迁移全程审计。

验收

构造 v1→v2 含节点删除、重命名、边条件变化的实例集；预演报告准确列出冲突；试迁 1 个实例后状态与令牌位置正确；回滚后字节级一致。

约束

P2 交付；M1–M3 只需保证「不迁移也完全正确」，这是绝大多数业务的真实需求。

14.6 表单权限矩阵与越权防护

为什么难

同一表单在 5 个节点有 5 套字段权限；前端隐藏不等于安全；退回重提后权限又变；子表单行级数据也要过滤。

方案

绑定矩阵作为唯一权威；服务端统一过滤器；隐藏字段不返回；越权写入丢弃并审计；表单版本钉住；退回后按目标节点权限重新计算。

验收

用审批人 token 直接构造包含只读/隐藏字段的请求，断言字段未落库且审计有记录；五个节点切换时权限矩阵渲染与提交结果一致。

性能

矩阵随快照缓存；过滤器只做内存判断，不产生额外查询。

14.7 脚本沙箱

为什么难

Python 默认能力过强：文件、网络、反射、无限循环。业务脚本由非安全专家编写，沙箱既要够用又要防逃逸。

方案

独立 Runner 进程池 + 无网络/只读 FS/cgroup；AST 检查 + import 白名单 + 受限内置；超时硬杀；输入输出限长；确定性 now/rand。

验收

安全用例：import os、open()、socket、死循环、内存炸弹、超大返回值全部被拒绝或超时；正常脚本性能 P99 < 100ms（不含排队）。

演进

如需 JVM 内执行，可评估 GraalPy；Runner 协议不变，内核无感知。

14.8 事务边界与外部调用

为什么难

HTTP 调用可能耗时数秒；把它放进数据库事务会长时间持锁、拖垮连接池；放外面又可能「调用成功但状态没落库」。

方案

两阶段作业：先在事务外调用（带幂等键），再开短事务写结果；失败按重试/onError/挂起处理；事件走 Outbox。

验收

注入慢接口（5s）时，实例锁等待与连接池占用不升高；调用成功后杀进程，重试不会造成重复业务效果。

原则

数据库事务内只做内存计算与本地写，绝不做网络 IO。

14.9 定时器规模化

为什么难

百万实例 × 多个超时/提醒，定时器数量大；精确到秒会带来高频扫描；实例挂起、工作日历、时区让「到期」不再是简单时间比较。

方案

定时器表 + 部分索引 + 批量领取；按分钟分桶降低扫描量；挂起时暂停并重算；工作日历缓存；提醒链式创建下一次。

验收

100 万条 PENDING 定时器下，扫描器单次领取 < 50ms；同一秒 10 万条到期时无大面积延迟；挂起/恢复后到期时间正确。

可观测

定时器延迟分布、单次扫描耗时、待触发数量。

14.10 Outbox 与消息重复

为什么难

业务事务与消息发送无法原子；RocketMQ 至少一次投递意味着重复；消费者可能先收到事件再看到数据库提交（不会，但重放会）。

方案

事务内写 Outbox；Relay 发送后标记；消费端按 event_id 去重；Webhook 带 delivery id；重放工具按事件重新投递。

验收

人为重复投递同一事件 10 次，通知只发 1 次、Webhook 只成功 1 次；Outbox 积压恢复后无丢失。

顺序

不承诺全局顺序；同一实例的事件带 instance_id 作为消息 key，RocketMQ 顺序队列保证实例内有序（可选）。

14.11 百万实例的存储与查询

为什么难

运行态与历史数据混在一张表，索引膨胀；列表页深分页；审计和变量日志增长最快。

方案

按月分区；完成实例归档；游标分页；覆盖索引；审计只追加并分区；只读副本承担列表与报表。

验收

1800 万实例下，待办列表 P99 < 200ms；实例详情 < 300ms；归档任务不影响在线写入。

放弃项

本期不做分库分表；单主库 + 分区足以覆盖首年目标，过早分片会增加事务与运维复杂度。

14.12 设计器与表单渲染器的复杂度

为什么难

流程画布、表单设计器、动态渲染器、权限矩阵四个编辑器叠加，容易走向「低代码平台失控」。

方案

严守 PRD 边界：不做像素级自由布局、不做通用 CRUD；字段类型按 MVP 清单冻结；渲染器用注册表扩展；复用同一套校验规则。

验收

新增一种字段类型只改「组件 + 校验器 + 后端类型」三处；S1/S2 两张表单从设计到发布全流程可自助完成。

性能

画布 200 节点可流畅拖拽；50 字段表单首屏 < 1s；子表单 200 行不卡顿。

14.13 审批人解析与组织可用性

为什么难

审批人依赖组织架构，组织服务不可用或数据滞后会导致任务无人可派；空集处理不当会静默自动通过。

方案

本地镜像 + Redis 缓存 + 定时同步；空集默认指派管理员并挂起；离职审批人标记并告警；设计期模拟解析。

验收

组织服务宕机时新实例仍可创建（使用镜像）；空集策略按配置生效；模拟解析对 100 个典型用户返回正确候选人。

数据新鲜度

镜像表带 source_version 与同步时间，页面显示「组织数据更新于 X」，超阈值告警。

14.14 多租户隔离

为什么难

行级隔离容易在某个查询漏加 tenant 条件；缓存、消息、对象存储路径都可能串租户。

方案

Repository 层统一注入租户；SQL 审计规则；缓存 key 与 MinIO 路径带租户前缀；跨租户操作只允许平台管理员且留审计。

验收

跨租户访问测试：A 租户 token 访问 B 租户实例/任务/附件全部 404；代码扫描无裸表查询。

时机

表结构从第一天就带 tenant_id；功能开关放 P2，避免后期迁移。
