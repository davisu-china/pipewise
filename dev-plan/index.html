00培养目标与总体思路

这不是「跟着视频敲一遍」的课程，而是让学员在真实约束下完成一个可运行、可演示、可运维的流程引擎。每期结束必须能跑起来、能演示、能讲清楚设计取舍。

能力目标

掌握 Java 21 / Spring Boot / PG / Redis / MinIO / RocketMQ 的工程化用法；能独立设计表结构、状态机、幂等与事务边界；能写 React 设计器与动态表单。

工程目标

产出可部署的 server/、web/、script-runner/；CI 全绿；S1/S2/S3 三个场景可演示；有压测与故障恢复记录。

教学方式

每期「设计评审 → 分工开发 → 中期集成 → Demo 验收 → 复盘」。讲师只做架构守门与 Code Review，不替学员写核心逻辑。

难度曲线

P2（执行内核）与 P4（网关/脚本）是分水岭；P5（表单）工作量最大。优先保证这三期质量，其余期可压缩。

建议的前置基础

  • Java：集合、泛型、异常、Maven、Spring Boot 基础（能写 REST 接口与 JDBC）。
  • 数据库：SQL、索引、事务、简单 EXPLAIN。
  • 前端：JavaScript/TypeScript、React 基础、CSS 布局。
  • 工具：Git 分支与 PR、Linux 命令行、Docker 基础。

基础不足的学员在开营前完成「Java Web 最小 CRUD + React 列表页」热身作业，避免 P0 就被环境卡住。

02开发节奏与协作规范

每周节奏

时间活动时长产出
周一本期 Kickoff + 设计评审60–90 min任务拆解、接口/表结构冻结
周二–周四开发 + 每日站会15 min / 天阻塞项当天暴露
周三中期集成检查30 min前后端联调、契约对齐
周五Demo + Code Review + 复盘90 min可运行演示、Review 记录、Retro

分支与合并

  • main 是唯一长期分支，任何时刻必须可构建、可启动。
  • 学员使用短期分支：feat/p2-<姓名>-token-engine，完成后发 PR，至少 1 人 Review，CI 通过后合并。
  • 每期结束打 tag：phase-0 … phase-8，方便回看与回滚。
  • 禁止直接 push main；禁止 force push；禁止提交密码、.env、构建产物。
  • 如果班级坚持直接在 main 提交，则要求小步提交、每次提交前本地跑测试，并由讲师每日抽查。

提交与 PR 规范

feat(engine): 令牌到达并行 join 时持久化 scope
fix(task): 竞签并发提交只允许第一个生效
docs(api): 补充实例创建接口的幂等说明
test(sign): 补或签全否决的裁决用例

PR 描述必须写：改了什么、怎么验证、影响范围、截图/日志（如适用）。

04P0 环境与工程基线

PHASE 0

环境与工程基线

第 1 周

教学目标

把「能开发、能提交、能运行」这件事先跑通：Maven 多模块、Spring Boot、Flyway、CI、React 工程、四个中间件连接。避免后面把时间浪费在环境和协作上。

后端任务

  • 建 server/ 多模块：pw-common、pw-api、pw-worker、pw-engine（空骨架）。
  • Spring Boot 3.5 + Java 21；/api/v1/ping、Actuator health；统一错误结构与 traceId。
  • Flyway 建库基线；配置文件分环境；日志输出到文件与 stdout。
  • 写一个 InfraSmokeTest：连 PG 执行 select 1、Redis ping、MinIO health、RocketMQ 发送一条测试消息。

前端任务

  • Vite + React 18 + TypeScript + Tailwind + shadcn/ui；应用壳、路由、API client。
  • 一个「环境自检」页面：显示 API、PG、Redis、MinIO、RocketMQ 的连通状态。

测试 / DevOps

  • GitHub Actions：mvn test、npm run build、前端单测；PR 必须绿。
  • 分支保护、PR 模板、Issue 模板；.gitignore 覆盖 target、node_modules、.env。

交付物

可启动的 api/worker 骨架、前端自检页、CI 流水线、环境说明 README。

验收门槛：新同学按 README 从零启动成功；CI 全绿；自检页四项全绿；提交一个 PR 并完成 Review。

对应文档：技术方案 §2、§12.1；中间件手册第 1–3 节。

05P1 定义、版本与设计器

PHASE 1

定义、版本与设计器

第 2–3 周

教学目标

理解「定义 / 版本 / 快照」三层关系，以及为什么发布后不可变。学会用 React Flow 做一个能保存、能校验的最小画布。

后端任务

  • wf_definition、wf_definition_version 表与 API；草稿乐观锁 draft_rev。
  • 快照 JSON 结构（节点/边/变量/表单引用）；SHA-256 内容哈希。
  • 发布前校验：唯一 start、至少一个 end、入边/出边、XOR 默认边、变量引用、脚本引用。
  • 发布生成不可变版本；默认版本切换；版本列表。

前端任务

  • 定义列表、新建/编辑草稿、发布按钮。
  • React Flow 画布：start/end/approval/exclusive 节点、连线、条件边、右侧配置面板。
  • 保存草稿、发布、校验错误定位；JSON 导入导出。

交付物

能把 S1 的图（start → 主管审批 → 条件分支 → end）画出来、保存、发布 v1，并看到版本列表与快照哈希。

验收门槛：非法图被阻断并给出原因；发布后再次修改只能生成 v2；刷新页面草稿不丢。

对应文档：技术方案 §6、§12.3、附录 17.1。

06P2 执行内核最小闭环

PHASE 2

执行内核最小闭环

第 4–5 周

教学目标

这是全课程最重要的一期。理解令牌、节点实例、作业队列、实例级串行、幂等与崩溃恢复。做完这一期，学员应该能解释「为什么任务完成不会重复推进」。

后端任务

  • 建 wf_instance、wf_token、wf_node_instance、wf_execution_job、wf_task、wf_audit_log、wf_event_outbox。
  • 创建实例（businessKey 唯一）、启动、start/end/approval 执行器。
  • Worker：SKIP LOCKED 领取作业、租约、心跳、失败重试；实例级 advisory lock。
  • 任务完成：CAS 校验、写审计、流转令牌；重复提交空操作。
  • 崩溃恢复测试：处理中 kill worker，重启后实例继续。

前端任务

  • 实例列表/详情、任务中心（待办/已办）、任务详情与同意/否决。
  • 实例时间线：节点激活、任务创建/完成、状态变化。

交付物

最小 S1：创建实例 → 主管待办 → 同意 → 实例完成；作业与令牌状态可查询。

验收门槛：同一任务 50 并发提交只成功一次；kill worker 后重启不重复流转；时间线与数据库状态一致。

对应文档：技术方案 §3、§4、§11.1–11.3。

07P3 签核与退回

PHASE 3

签核与退回

第 6–7 周

教学目标

把 PRD 第 8 章的语义翻译成代码：任务与会话分离，三种签核模式用同一个裁决函数；退回/撤回/重提的轮次要能解释清楚。

后端任务

  • wf_sign_session；ANY / ALL / RACE 裁决；并行/串行会签；通过比例与一票否决。
  • 加签、转交、委托、改派；任务动作流水。
  • 退回 to_start / to_prev / to_node / terminate；撤回；重提轮次 round 与保留已通过节点。
  • 审批人解析器：user / role / managerOf / deptLeader / initiator / expr；空集与离职策略。

前端任务

  • 设计器：签核模式、通过规则、退回策略、审批人解析器配置。
  • 任务页：加签/转交/退回/撤回/催办；审批记录与意见。

交付物

S2 采购合同场景：金额 > 50 万走三方并签，≤ 50 万走竞签；退回后重提。

验收门槛：三种模式 × 同意/否决/加签/转交的决策表用例全过；竞签并发只产生一个结论；退回后时间线可解释。

对应文档：技术方案 §5、§8.2。

08P4 网关、上下文与脚本

PHASE 4

网关、上下文与脚本

第 8–9 周

教学目标

第二个分水岭。理解并行 fork/join 的令牌语义、join scope、死锁检测；理解变量作用域与并发写保护；跑通一个最小脚本沙箱。

后端任务

  • XOR / AND / OR 网关；wf_join_scope；嵌套深度与步数保护；死锁告警。
  • 变量作用域（FLOW/NODE/ENV）、声明与类型、版本号乐观锁、冲突策略、变量审计。
  • Aviator 白名单表达式；编译缓存；求值超时。
  • 脚本 Runner：独立进程/容器、超时、内存限制、白名单 API、试算接口、重试与 onError 边。

前端任务

  • 设计器：网关 fork/join 配对、条件边、变量声明面板。
  • 试跑（Dry Run）：输入变量 → 高亮路径 → 展示每步变量变化。
  • 实例时间线展示并行分叉/汇聚与脚本输出。

交付物

S1 完整版：主管审批 → 并行「HR 备案 + 总监审批」→ 汇聚 → 脚本算年假 → 结束。

验收门槛：并行分支全部到达才汇聚；分支被跳过时能告警；脚本超时/报错按策略处理；kill worker 后汇聚状态可恢复。

对应文档：技术方案 §3.6、§8。

09P5 表单引擎

PHASE 5

表单引擎

第 10–12 周

教学目标

工作量最大的一期。重点不是画表单，而是「同一张表单在不同节点对不同人呈现不同权限」，且服务端不可被前端绕过。

后端任务

  • wf_form / wf_form_version / wf_form_binding / wf_form_data；表单版本钉住。
  • 字段权限矩阵解析：HIDDEN / READONLY / EDIT / EDIT_REQUIRED；默认只读/继承。
  • 三层校验；服务端权限过滤与越权字段丢弃；计算字段服务端复算。
  • 子表单、行数上限、附件 MinIO 预签名、草稿。
  • 表单提交与任务完成同一事务。

前端任务

  • 表单设计器：字段面板、布局、属性、预览、移动端预览。
  • Schema 渲染器：字段注册表、权限过滤、子表单、联动、计算、附件上传。
  • 节点 × 字段权限矩阵编辑器（表格视图、批量填充、继承）。

交付物

S4：一张费用报销单绑定 5 个节点，字段权限随节点变化；PC 与移动端均可填写。

验收门槛：审批人构造越权字段提交，服务端丢弃并审计；子表单超 200 行被拒；表单提交与任务完成同事务；旧实例按旧表单版本渲染。

对应文档：技术方案 §7、§12.4。

10P6 API、事件与通知

PHASE 6

API、事件与通知

第 13–14 周

教学目标

让流程引擎成为「可被业务系统调用的平台」：开放 API、幂等、Outbox、RocketMQ、Webhook、通知与定时器。

后端任务

  • 开放 REST API：创建/查询/挂起/恢复/终止、任务查询/完成、版本列表/发布。
  • Idempotency-Key、错误码、游标分页、OpenAPI 文档。
  • Outbox Relay → RocketMQ；事件清单；消费去重；Webhook 签名、重试、死信。
  • 站内信/飞书通知、模板、去重；定时器与超时策略、工作日历。

前端任务

  • API 文档页、Webhook 订阅管理、投递记录。
  • 通知中心与角标；定时/超时策略配置。

交付物

外部系统可通过 API 创建实例并订阅事件；Webhook 失败可重试；定时提醒可触发。

验收门槛：同幂等键重复请求只产生一个实例；事件重复投递不重复通知；Webhook 失败进入死信并可重放；定时器重启后不丢。

对应文档：技术方案 §9、§10。

11P7 运维、观测与压测

PHASE 7

运维、观测与压测

第 15–16 周

教学目标

从「能跑」到「敢让人用」：能定位卡点、能人工干预、能扛住峰值、能在故障后恢复。

后端任务

  • 运维干预：强制通过/否决、跳过、跳转、重跑、终止、改变量；二次确认与审计。
  • 指标：作业积压、单步耗时、脚本失败率、Outbox 积压、卡住实例；OpenTelemetry traceId。
  • 分区、归档、慢查询治理；压测脚本与容量报告。

前端任务

  • 运维控制台：卡点实例、作业积压、失败节点、干预操作。
  • 监控大盘：实例状态分布、任务积压、节点耗时、回调失败。

交付物

一份压测报告、一份故障演练记录、一个可用的运维控制台。

验收门槛：kill worker / 停 MQ / 停 Redis 三种故障下核心流程不丢状态；卡住实例能被发现；干预操作全部留审计。

对应文档：技术方案 §13、§14。

12P8 结业演练

PHASE 8

结业演练

第 17–18 周

教学目标

把前 8 期拼成完整产品，按真实评审标准做一次交付：三个场景、一次部署、一次答辩。

任务

  • 回归 S1（请假）、S2（采购合同）、S3（长跑 + 版本升级）。
  • 安全评审：越权、脚本沙箱、敏感字段、附件、Webhook 签名。
  • 部署到测试环境；写运维手册与故障处理手册。
  • 每组 20 分钟演示 + 10 分钟答辩：为什么这样设计、哪里还会出问题。

交付物

release tag、部署地址、演示视频/录屏、个人总结、组内互评。

验收门槛：三场景全部跑通；代码评审无阻塞项；部署可复现；答辩能解释令牌、幂等、签核、表单权限四个核心问题。

13环境与数据隔离

班级共用一套中间件时，必须做命名空间隔离，否则会互相覆盖数据、抢 Topic、误删桶。

组件隔离方式示例
PostgreSQL每组一个 schemaCREATE SCHEMA student_team1; 所有表放该 schema
Rediskey 前缀或不同 dbteam1: 前缀；或用 db 1–15
MinIO每组一个桶或目录student-team1 桶，或 student/team1/ 前缀
RocketMQTopic / Group 前缀team1_order_topic、team1_order_group
凭据使用红线 中间件账号密码只通过环境变量/.env 注入，.env 必须被 gitignore；禁止把密码写进代码、配置文件、截图、PR 描述。课程结束后统一轮换密码。

推荐的环境分层

  • 本地：Docker Compose 起 PG/Redis/MinIO/RocketMQ，便于随意重置。
  • 共享集成环境：统一中间件 + 每组命名空间，每周五 Demo 用。
  • 结业环境：独立部署，使用 release tag，保留演示数据。

14质量与验收标准

完成的定义（DoD）

  • 功能可演示，主路径与至少一个异常路径都验证过。
  • 核心逻辑有单元测试；数据库相关有集成测试；关键并发有压测/并发用例。
  • 接口/表结构变更同步更新文档；PR 描述写清验证方式。
  • 没有提交密钥、构建产物、本地配置；CI 绿。
  • 至少 1 人 Review 通过；讲师抽查关键模块。

Code Review 检查清单

维度检查点
正确性状态机是否单调？令牌是否只消费一次？事务边界是否包含状态+事件？
幂等重复请求/重复消息/双击提交是否安全？
并发实例锁、任务 CAS、变量版本冲突是否处理？
安全越权字段、脚本白名单、SSRF、敏感数据脱敏是否覆盖？
可测核心逻辑是否可脱离数据库测试？异常路径是否有用例？
可读命名、分层、注释是否解释了「为什么」而不是「做了什么」？

15考核与结业

每期评分（100 分）

项权重标准
功能完成度50验收门槛全部通过，异常路径可用
测试20核心单测 + 集成/并发用例，CI 稳定
代码质量15分层清晰、命名合理、无重复实现、Review 通过
演示与文档15能讲清楚设计取舍；PR/文档完整

结业成绩

  • 阶段平均分 60% + 结业项目 30% + 参与度（Review/分享/互助）10%。
  • 红线：无测试、提交密钥、直接 push main、抄袭他人代码——该期记 0 分并复盘。
  • 优秀作品：代码合并进主仓库、部署演示、写成技术分享。
