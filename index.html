01背景与目标

1.1 背景

公司内部流程（报销、采购、入职、合同、发布审批、权限申请等）目前散落在多套自建审批代码与第三方 SaaS 中，存在三类共性问题：

  • 不可视——流程逻辑写死在业务代码里，改一个审批人要走发版；业务方无法自助调整。
  • 不可控——没有统一的实例视图，审批卡在谁那儿、卡了多久、为什么卡，只能翻日志。
  • 不可复用——并签、竞签、退回、加签、超时这些通用能力，每个业务线各写一遍，语义还不一致。

本平台的目标是提供一层流程基建：业务方在可视化设计器里定义流程 → 发布成不可变版本 → 业务系统调用 API 创建实例 → 引擎驱动节点流转、生成待办、执行脚本与并行分支 → 全过程可追溯、可干预。

1.2 产品目标

  • G1 定义即运行：业务方不写代码即可完成「定义 → 发布 → 创建实例 → 跑通」的闭环。
  • G2 长跑可靠：实例可存活数天到数月，跨服务重启、跨版本迭代不丢状态、不重复流转。
  • G3 语义统一：签核（或／并／竞）、退回、加签、超时、撤销等企业审批语义，全平台一套定义、一处实现、处处一致。
  • G4 可编程：节点内可写脚本做参数计算与条件判断，流程上下文是一等公民，脚本可读可写、可审计。
  • G5 可运维：任一实例能回答「现在在哪、谁在等、为什么等、下一步是谁」，并支持人工干预（改派、跳过、终止、回滚）。

1.3 非目标（本期不做）

  • 不做通用 RPA／爬虫类自动化执行器。
  • 不做完整 BPMN 2.0 兼容（不追求全量事件子流程、补偿边界事件等冷门特性，按需裁剪）。
  • 不做脱离流程的通用低代码平台。表单引擎只服务流程节点（见第 10 章），不做独立 CRUD 应用、不做通用报表 BI、不做像素级自由布局的页面编排。
  • 不做 AI 智能审批决策（预留扩展点，见附录 A）。

1.4 设计原则

定义与实例分离

流程定义是「图纸」，实例是「按图纸造出来的东西」。定义改版不影响已跑实例——图纸可换，房子不塌。

版本不可变

已发布版本只读。任何修改产生新版本，实例永远钉在创建它的那个版本上（长跑实例迁移是显式操作，见 6.4）。

令牌驱动

实例执行状态用「令牌（Token）」在图上流动来描述，天然支持并行分叉与多令牌汇聚，而非用状态字段硬编码。

一切可追溯

变量变更、任务动作、节点流转、脚本输出全部落审计流水，任何一次状态改变都能回答「谁、何时、基于什么」。

关键设计判断

节点是「类型 + 配置」，不是「类」。引擎只认识有限的几种节点类型（见 5.3），业务差异全部由「配置 + 脚本」表达。这样新增一种业务审批不需要改引擎、不需要发版，符合基建定位。

3.1 端到端核心场景（验收主线）

场景 S1：请假审批（主干闭环）

员工提交 3 天请假 → 直属主管审批（或签：主管或代理主管任一通过）→ 若天数 > 2 天，并行触发「HR 备案」与「部门总监审批」两条分支 → 两分支汇聚 → 脚本节点计算剩余年假并写回上下文 → 结束并回调 HR 系统。

场景 S2：采购合同（并签 + 竞签混合）

金额 > 50 万走「法务 + 财务 + 风控」三方并签（须全部同意，任一否决则整单否决）；金额 ≤ 50 万走「任一业务负责人竞签」（第一个处理的人定音，其余任务即刻回收）。

场景 S3：长跑实例 + 版本升级

某入职流程实例停留「等待背调结果」节点 12 天。期间流程定义发布了 v3（新增一个节点）。旧实例继续在 v2 上运行到结束，不被强制迁移；管理员可选择对新实例生效 v3。

场景 S4：同一张表单，不同节点不同权限

一张「费用报销单」绑定在流程的 5 个节点上。发起节点：申请人可编辑「金额 / 明细 / 发票附件」，看不到「审批结论」；主管审批节点：金额与明细变为只读，新增可编辑的「主管意见·必填」；HR 备案节点：新增可编辑的「备案号」；总监节点：可编辑「审批结论」。同一张表单，随节点滑动切换字段角色——这是自建表单引擎相对外部表单系统的核心增量。

05流程建模与设计器

5.1 建模要求

  • 画布：拖拽节点、连线、对齐吸附、自动布局、缩放平移、撤销重做。
  • 节点配置面板：右侧抽屉，按节点类型渲染不同配置表单。
  • 实时校验：图结构校验在保存前实时提示（见 5.5）。
  • 试跑（Dry Run）：不落真实数据，模拟变量输入，看到流转路径与每个节点的进出，验证分支条件与脚本。
  • JSON 双向：设计器 ⇄ 流程 JSON 快照可互转，允许研发用 JSON/YAML 直接定义并导入。
  • 协作：草稿支持多人编辑与锁定，发布动作单人串行。

5.4 表单绑定

本平台自带表单引擎（见第 10 章）。人工节点通过 formRef 绑定一张表单，并配置字段级权限矩阵（本节点 × 每个字段 = 隐藏／只读／可编辑／必填）。表单字段名直接映射为上下文变量名，提交即写上下文。

同时保留外部表单嵌入通道作为兜底：节点可用 formRef 指向外部表单 URL（历史系统 / 复杂定制表单），以 iframe 或微前端嵌入，平台只负责校验与结果写回。内置表单引擎覆盖 95% 的常规审批场景，外部嵌入用于兜底的长尾。

5.5 保存前校验（阻断发布）

  • 必须有且仅有一个 start；至少一个 end。
  • 所有节点必须有入边（start 除外）与出边（end 除外）。
  • 分支节点（排他/包容）的默认边必须存在，或有「无匹配则报错」的显式配置。
  • 并行 fork 与 join 必须成对且所在分支闭合（结构正确性）。
  • 所有表达式中引用的变量必须在 variables 中声明或由上游节点保证产出。
  • 脚本语法检查 + 静态引用检查（只允许白名单 API）。
  • 审批节点的审批人解析器必须能解析出候选人（配置期做「模拟解析」）。

06发布与版本管理

6.1 版本状态机

草稿 DRAFT→ 已发布 PUBLISHED→ 已下线 RETIRED
  • 草稿：可随意编辑，不进实例。
  • 已发布：生成不可变快照，版本号自增。可配置生效时间、生效范围（灰度：按租户/发起人/比例）。
  • 已下线：不再允许新实例使用；已在跑的实例不受影响，继续按原版本执行完毕。

6.2 版本规则（硬约束）

规则说明
版本不可变发布后任何修改都生成新版本，历史版本永久保留，用于审计与回溯。
实例钉版本实例创建时记录 version_id，运行期只读该版本快照，绝不随定义更新而改变行为。
默认版本每个 definition 有且仅有一个「当前默认版本」，业务系统按 key 起流程时使用；可手动切换。
版本对比提供图级 diff：新增/删除/修改的节点、边、变量、脚本。
下线保护若仍有运行中实例钉在该版本，下线只阻断新实例并给出提示，不回收旧实例。

6.3 发布流程

提交发布设计者
→
自动校验结构+脚本+变量
→
试跑回归用例集
→
审批发布流程管理员
→
生效灰度/全量

支持配置「无需审批直接发布」的快捷通道（用于低风险测试流程），但生产租户默认强制走审批。

6.4 长跑实例迁移 P2

这是流程引擎最难的问题，也是最有价值的积累

默认策略是不迁移——旧实例跑完旧版本，这是最安全也最常规的做法。当业务确实需要（如旧版本有 bug 需紧急修复）时，提供显式迁移工具：

  • 可预演：给定版本 A → 版本 B，计算所有受影响实例，输出「哪些实例的当前节点在 B 中已不存在／语义已变」的冲突报告。
  • 活动映射（Activity Mapping）：为每个冲突节点指定迁移目标（等价节点 / 跳过 / 回退到某节点）。
  • 可回滚：迁移前对实例打全量快照，迁移失败可一键回滚。
  • 灰度：按实例白名单先迁 1 个，验证通过再批量。
  • 迁移全过程落审计；迁移后的实例带 migrated_from 标记，时间线上可见。

07实例生命周期

7.2 实例与业务单的关系

  • 创建实例时必须携带 businessKey（业务单号），平台侧保证 (definition_key, businessKey) 唯一，天然防重复提交。
  • 实例可携带 title（待办列表展示用）与 initiator（发起人）。
  • 业务系统可通过 businessKey 反查实例状态；平台也可回调业务系统（Webhook）。

7.3 实例时间线

每个实例提供一条不可篡改的时间线，按时间倒序展示：节点激活、任务创建/认领/完成、变量变更、脚本执行与输出、并行分叉/汇聚、异常与重试、人工干预。这是排障与审计的主入口。

08审批与任务（签核体系）

这是本平台最核心、也最容易被做歪的部分。签核语义必须一次定义清楚，避免各业务线各写一套。

8.1 三种签核模式

模式KEY裁决规则典型场景
或签any N 个候选人同时收到任务；任意一人「同意」即节点通过，其余任务立即作废。若有人否决，节点不结束，仍等其他人处理（否决只是记录意见）。 主管或代理主管任一审批；值班人轮值审批
并签
（会签）		all N 个候选人全部完成节点才结束。通过条件可配：全部同意／同意比例 ≥ X%／一票否决。支持并行会签（同时发）与串行会签（按顺序逐个发）。 法务+财务+风控三方会签；委员会投票
竞签race N 个候选人同时收到任务；第一个处理的人的决定即为节点结论（同意或否决都算数），其余任务立即回收作废。 抢单式审批；多个负责人谁先有空谁定；竞价/抢标
或签 vs 竞签：一句话说清区别

或签是「谁先同意算谁赢」——否决不终结，别人还能救；竞签是「谁先出手谁定音」——第一个人的结论就是最终结论，哪怕是否决。两者都只产生一个有效结论，区别在于「否决是否终止流程」。

动作语义权限

会签加签向并签节点追加一个审批人，纳入同一裁决集合管理员

加签后签核语义：加签产生的任务纳入当前节点的裁决集合，遵循原签核模式（如竞签节点加签后仍是「先处理者定音」）。

重提语义（关键）：退回后重提，默认「保留已通过的审批结果、仅重走被退回及之后的节点」；可配置为「全部重走」。两种语义必须显式选择，不允许隐式默认导致歧义。

撤回：发起人在「无人处理前」可撤回整单，实例终止或回到草稿。撤回时间窗可配置（如：首个人工任务被处理前）。

结论字段 verdict：approve / reject / return。任务完成时写审计：操作人、时间、意见、附件、耗时。

8.5 审批人解析器

审批节点的 assignee 是一个解析器而非静态名单，运行期求值。内置解析器：

解析器含义

initiator流程发起人

09网关、并行与汇聚

9.1 排他网关（XOR）

按出边条件顺序求值，只走第一条满足条件的边。必须有默认边（条件恒真的兜底），否则运行期无匹配时报错。

# 出边条件示例（自上而下求值，命中即停）
"ctx.amount > 500000"                       # 大额
"ctx.amount > 50000 and ctx.dept == 'RD'"   # 中额且研发
true                                        # 默认边（兜底，必填）

9.2 并行网关（AND）与令牌汇聚

  • Fork：一条入令牌 → 全部出边各产生一条令牌，无条件全部激活（出边上的条件被忽略或禁止配置）。
  • Join：等待该网关所有入边各到达一条令牌，才合并为一条继续。未到齐则阻塞。
  • 同一并行分支内可嵌套并行（令牌数指数增长，需限制嵌套深度，默认 ≤ 3 层）。
  • 死锁保护：若某个 Join 因分支被条件跳过而永远等不齐，引擎在令牌空闲超阈值时告警，并提示结构性问题。

9.3 包容网关（OR）P1

Fork 时按条件激活一条或多条分支（至少一条）；Join 时只等「实际被激活过」的分支到齐。用于「满足条件的都走」类场景，比并行网关更灵活但也更易踩坑，需在 Join 处显式标记匹配范围。

9.4 并行分支示例

→

9.5 循环与步数保护

图允许回环（如「补充材料 → 重新提交」），但必须设实例最大步数（默认 1000）与单节点最大激活次数（默认 100），超限即挂起并告警，防止死循环打爆系统。

10表单引擎

流程里的「人」要干活，就得有地方填东西：申请人填报销单、审批人填意见、HR 填备案号。表单不是流程的附属功能，而是流程上下文的人机接口——用户在表单上敲的每一个字，就是上下文里的一次变量写入。

10.1 定位与边界

一句话定位

表单引擎是「流程驱动的表单」，不是「通用低代码平台」。它存在的意义是让每个节点上的人知道「我现在该填什么、能看什么」，而不是让人去搭一套独立的 CRUD 应用。

做不做
流程节点上挂表单，字段与上下文变量打通；字段级权限随节点变化；子表单录入明细；数据随实例归档与检索。 脱离流程的独立数据应用；完整的报表 BI 能力；复杂的前端页面编排（自定义组件、自由布局像素级拖拽）；通用工作流之外的业务系统建模。

10.2 表单与流程的关系（本章核心）

一个流程版本绑定一组表单：发起表单（start 节点）+ 各人工节点的表单。同一张表单可被多个流程、多个节点复用（表单是独立可复用资产，不与某个流程耦合死）。

字段级权限矩阵 —— 流程表单的灵魂

同一张表单，在不同节点上呈现给不同的人，每个字段的可见性与可编辑性由「节点 × 字段」决定。这是流程表单区别于普通表单的核心，也是审批场景的硬需求：申请人填的金额，审批人只能看不能改；审批人的意见，申请人看不到。

字段发起节点主管审批HR 备案总监审批结束归档
报销金额可编辑·必填只读只读只读只读
费用明细可编辑只读只读只读只读
主管意见隐藏可编辑·必填只读只读只读
HR 备案号隐藏隐藏可编辑·必填只读只读

表 10-1 字段级权限矩阵示例。「隐藏」= 字段根本不渲染；「只读」= 展示但灰化；「可编辑」= 可填写。

权限粒度到字段，而非到表单。一个节点若未配置某字段，则该字段按「继承上一节点」或「默认只读」处理（可配，默认只读）。

表单字段 = 上下文变量

表单字段名直接映射为上下文变量名。用户在表单提交的瞬间，字段值写入流程上下文；脚本节点修改上下文后，表单再次渲染时展示的是新值。这条双向绑定让「表单」和「上下文」成为同一份数据的两种视角，避免了两套数据模型对不上的经典问题。

10.4 子表单（明细表）

企业表单的重头戏——一次报销有多条费用明细，一次出差有多个行程段。子表单是「字段内嵌一个表格」，每行是一组同构字段。

  • 支持增删行、行内校验、行内计算、列合计（如金额汇总）。
  • 行数上限，默认 200 行，超限拒绝并提示（防打爆）。
  • 脚本可读写子表行（按行索引或整体数组）。
  • 子表不能直接作为流转条件——网关条件只认标量。需先用计算字段聚合（如「明细总额」「明细行数」）再判断。这是设计约束，不是缺陷：避免条件表达式里塞复杂度。

10.5 字段联动与计算

  • 联动规则：字段 A 变化 → 触发 B 的取值 / 显隐 / 必填 / 选项变化。例：选择员工 → 自动带出部门、职级、直属主管。
  • 计算字段：金额 = 单价 × 数量。前端实时计算仅用于展示体验，服务端在提交时复算并以服务端结果为准（前端可被篡改）。
  • 数据源：静态字典 / 接口动态拉取（带缓存与超时）/ 级联数据源。
  • 联动与计算的逻辑若复杂，落脚本：脚本节点统一处理上下文，表单只负责展示。

10.6 三层校验体系

层次时机作用
前端即时校验输入时 / 失焦体验：立刻提示格式错误，减少无效提交
服务端提交校验提交表单时可信防线：前端可绕过，服务端必须复校验
流转前校验节点完成、令牌流转前守门：关键字段缺失或非法时阻断流转

校验规则：必填、类型、长度、正则、数值范围、唯一性（如同名不可重复）、跨字段校验（表达式或脚本）、自定义异步校验（如「该发票号已被报销过」需查库）。校验失败返回结构化错误，定位到具体字段与行，前端高亮。

10.7 数据存储与检索

  • 表单数据存 wf_form_data（结构化 JSON + 实例关联），与流程实例同生命周期，实例归档时一并归档。
  • 字段可声明「可查询」：被标记的字段抽出为独立索引列（或入 ES），供实例列表检索、报表与外部查询。未标记的字段只存 JSON，不建索引，避免全字段索引拖垮写入。
  • 敏感字段（如银行卡号）加密存储 + 脱敏展示 + 访问审计。

10.8 草稿与暂存

  • 申请人可分多次填写，草稿态保存不启动流程实例。
  • 草稿可丢弃、可继续编辑、可复制上一条单据快速填。
  • 草稿数据与正式提交隔离，草稿不产生待办、不发通知。

10.9 渲染与多端

  • Schema 驱动动态渲染：表单以 JSON Schema 描述，前端解析渲染，不为每张表单写页面。
  • PC Web + 移动端（飞书 H5 / 小程序），同一 Schema 两套适配渲染器。
  • 打印/导出：表单 PDF 打印（含审批流转记录、意见、手写签名）；表单数据导出 Excel（需数据权限）。

10.10 表单设计器

  • 拖拽建字段、右侧属性面板、实时预览、移动端预览切换。
  • 表单 Schema 可导入导出（JSON），研发可代码化定义与版本管理。
  • 表单模板库：常用表单（报销单、请假单、采购申请）沉淀为模板，新流程直接套用。
  • 表单与流程版本的绑定关系可视化：哪些节点用了哪张表单、字段权限矩阵一目了然。

10.11 表单 API

方法路径说明
GET/api/v1/instances/{id}/form获取当前节点表单 Schema + 数据 + 字段权限（已按当前用户过滤）
POST/api/v1/instances/{id}/form/draft保存草稿
POST/api/v1/tasks/{id}/submit-form提交表单并完成任务（校验 + 写上下文 + 流转）
GET/api/v1/instances?form.field=按可查询字段检索实例

关键：表单提交与任务完成是同一个事务——校验通过、写上下文、写表单数据、完成任务、流转令牌，要么全成功要么全失败。不存在「表单存了但流程没走」的中间态。

10.12 与签核的交互

  • 并签：每个审批人各自提交自己的意见字段（如「法务意见」「财务意见」），字段权限按角色统一；所有人提交完节点才结束。
  • 竞签：第一个提交者的表单数据即生效，其余人的任务回收，其填了一半的数据作废。
  • 退回：退回后申请人能编辑的字段由权限矩阵决定（通常是发起节点可编辑的字段）。
  • 审批意见是系统内置字段，与业务字段分开存储与展示，便于统一生成流转记录。

11流程上下文系统

10.1 作用域

作用域可见范围生命周期
流程级 ctx全实例可见实例创建 → 实例结束
节点局部 local仅当前节点实例节点激活 → 节点结束（并行各分支独立）
子流程级子流程内可见子流程实例生命周期

子流程通过 输入映射（in）与输出映射（out）与父上下文交互，默认不共享变量（隔离优先），共享需显式声明。

10.2 变量类型与契约

类型说明备注
string / number / bool基础类型number 含精度配置（金额建议 decimal）
date / datetime时间存储 UTC，展示按用户时区
json / object结构化数据支持 JSON Schema 校验

变量在流程定义的 variables 中声明：名称、类型、是否必填、默认值、是否敏感（脱敏展示）、是否只读。未声明的变量写入时按宽松模式允许但记审计，或按严格模式拒绝（可配，默认宽松）。

10.3 变更审计

每一次变量写入落一条流水：instance_id、variable、old_value、new_value、actor（脚本/用户/系统）、node_instance_id、timestamp。敏感变量在审计中脱敏。这是「为什么金额被改成这样」的唯一真相来源。

10.4 并发写保护

并行分支同时写同一变量 = 数据竞争

并行分支各自持局部变量，写回流程级变量时采用 写时快照 + 版本号乐观锁：若变量在读取后已被其他分支修改，本次写入失败并按配置处理（重试 / 报错挂起 / last-write-wins 记告警）。流程设计器对「多分支写同一变量」给出结构性告警。推荐模式：各分支写自己的局部变量，在 Join 后的脚本节点统一汇总写回。

10.5 表达式语言

边条件与轻量计算使用受限表达式语言（类 SpEL/EL 的子集），支持：变量引用、比较、布尔运算、in、简单内置函数（len/contains/daysBetween 等）。表达式不产生副作用，只读。复杂逻辑一律落到脚本节点。

12节点脚本与服务节点

11.1 脚本节点能力

  • 语言：Python（主）。表达式语言覆盖简单场景，脚本覆盖复杂场景。
  • 入口约定：脚本定义 def run(ctx, local, env, logger, now)，返回 None 或 dict（增量写回局部变量）。
  • 可用 API（白名单，沙箱注入）：ctx.get/set、local.get/set、env.get、logger.info、now()、user(id)、org(id)、json、datetime、decimal、math、re。
  • 禁止：网络访问、文件系统、import 非白名单模块、随机数（除非用注入的 rand(seed)）、读系统时间（用注入的 now 保证可重放）。
  • 资源限制：超时（默认 3s）、内存上限（默认 256MB）、CPU 时间上限。

11.2 脚本示例

# 节点：计算差旅补贴并决定是否需要总监审批
def run(ctx, local, env, logger, now):
    days  = ctx.get("trip_days", 0)
    level = user(ctx.get("applicant_id")).level
    rate  = {"P5": 300, "P6": 500, "P7": 800}.get(level, 200)

    allowance = days * rate
    need_vp   = allowance > 5000

    logger.info(f"allowance={allowance} need_vp={need_vp}")
    return {"allowance": allowance, "need_vp": need_vp}

图 11-1 脚本节点示例。返回值增量写回局部变量，由节点显式映射到流程级变量。

11.3 异常与重试

策略行为
重试可配次数与退避（如 3 次，指数退避）；幂等由运行时保证
onError 边失败走指定出边（如转到人工处理节点）
挂起无兜底时实例置 FAILED，等运维修复后重跑该节点
忽略仅对非关键脚本允许（显式配置）

11.4 服务节点 P1

  • HTTP 调用：URL 模板、方法、Header、Body 映射（上下文 → 请求体）、响应映射（响应 → 上下文）。超时、重试、熔断。
  • MQ 投递：向指定 topic 投消息，可选同步等待回执。
  • 异步等待：服务节点发起后挂起，等外部回调（带签名校验的 Webhook）唤醒，超时则走超时策略。
  • 幂等：所有对外调用带幂等键（实例+节点实例+尝试次数），下游需支持。

13通知、超时与运维干预

12.1 通知

  • 渠道：站内信、飞书（机器人/卡片）、邮件、短信（可扩展）。
  • 触发点：任务创建、任务被转交、超时提醒、流程结束、被退回。
  • 去重：同一任务同一事件的通知幂等（防止重复轰炸）。
  • 模板：支持变量插值，模板与流程解耦、可运营配置。

12.2 超时策略

策略行为
提醒N 小时后催办，可多次、可升级到上级
自动通过超时视为同意（需显式开启，默认关闭）
自动否决超时视为否决
自动转交转给代理人或上级
仅告警只通知管理员，不自动动作

超时计时暂停语义：实例挂起或非工作时段是否计时，按节点配置；支持工作日历（跳过周末/节假日）。

12.3 运维干预

操作说明影响
强制通过/否决管理员代为完成当前任务记审计
跳过节点跳过当前节点直接流转记审计
跳转到节点把令牌移动到任意节点（危险操作）需二次确认+审计
重跑节点重新执行失败的脚本/服务节点幂等保护
终止实例回收所有令牌与在途任务终态
修改变量直接改上下文变量（危险操作）需审批+审计

所有干预操作走二次确认，写审计流水，可配置是否需要「第二人复核」（四眼原则）。

15非功能需求

14.1 一致性

  • 状态与事件同事务：节点流转、任务生成、变量写入、事件入 Outbox 在同一数据库事务内完成，杜绝「任务生成了但事件没发」。
  • 幂等：所有状态转移以「节点实例 + 尝试序号」为幂等键，重复投递不产生重复流转。
  • 仅一次语义（近似）：人工任务严格一次；脚本节点至少一次 + 幂等保证效果等价于一次；外部调用依赖下游幂等键。

14.2 性能目标

指标目标口径
实例创建吞吐≥ 1000 / 秒集群峰值，含事务与事件落库
实例创建延迟P99 < 300ms同步返回实例 ID
任务完成到下一步激活P99 < 500ms含脚本执行
待办列表查询P99 < 200ms按 assignee 索引
单实例并发令牌≤ 100超限告警
在跑实例量百万级需分区与归档

14.3 高可用与可扩展

  • 无状态服务节点，可水平扩展；调度与执行分离（调度器扫描待办触发器，Worker 执行节点）。
  • 数据库为主存储；热数据与历史数据分离（完成的实例定期归档）。
  • 故障恢复：进程崩溃后，未完成的事务回滚，已提交的事务由幂等保证不重复；定时器持久化，重启后继续。

14.4 可观测

  • Trace：从 API 请求 → 实例 → 节点 → 脚本，traceId 全链路贯穿。
  • Metrics：实例数/状态分布、节点耗时分布、任务积压、脚本错误率、超时率、回调失败率。
  • 日志：结构化日志，含 instance_id / node_instance_id / task_id。
  • 告警：实例卡住（同一节点停留超阈值）、脚本错误率突增、待办积压、回调堆积。

14.5 安全

  • 鉴权：API 走 Token/服务身份；审批操作校验「该任务确实指派给当前用户」。
  • 数据权限：申请人只看自己的单，审批人只看待办/已办，管理员按租户/部门范围看。
  • 脚本沙箱：见 12.1，禁网络/文件/危险 import，资源限额。
  • 审计：所有状态变更与干预永久留存，不可篡改（append-only）。
  • 敏感数据：标注为敏感的变量脱敏展示、加密存储。

14.6 多租户 P2

租户维度隔离定义、实例、变量与权限；共享引擎与调度集群，按租户配配额（并发实例数、日创建量）。存储行级隔离，管理端可跨租户运维。

A附录：技术选型结论（沿用前两轮调研）

本附录不是 PRD 主体，是给技术决策者的输入，结论来自本项目前两轮调研，不重复展开。

结论一：执行内核不自研

durable execution（持久化执行）这件事——崩溃恢复、至少一次投递、幂等重放——是极深的坑，自研必踩。建议在 DBOS / Restate / Temporal 中三选一，作为底层执行内核嵌入；本方只做上层「图模型 + 节点/边 + 业务编排 + 设计器 + 开放 API」。

结论二：Python 栈的传统 BPMN 引擎，唯一能打的是 SpiffWorkflow

若确需完整 BPMN 语义（事件子流程、边界事件等），SpiffWorkflow（LGPL-3.0）是 Python 生态里唯一成熟选项，可作为参考实现或直接嵌入。注意 LGPL 的合规边界。

结论三：最该抄的是版本化与实例迁移

传统引擎（CIB seven、Operaton 等）今年都在长 AI 能力，但在流程定义版本化与长跑实例迁移上积累深厚——这恰是自研最容易做薄的地方。本文第 6 章（版本管理）与 6.4（迁移）即据此设计，建议直接借鉴其成熟方案而非自创。
